# Design

## Context

见 `proposal.md` 的 Why。密钥表由 `client_keys` 承载，现有接口只有列表、新建与启用/停用。快照在密钥变更后刷新，鉴权读快照。删除需要沿用这条刷新路径，否则被删密钥仍能通过鉴权。

## Goals / Non-Goals

**Goals:**

- 删除即时生效，不重启进程。
- 删除不可误触，必须输入名称。

**Non-Goals:**

- 不做软删除，不留审计表。
- 不改密钥哈希与新建方式。

## Decisions

### 1. 删除走硬删除

`DELETE FROM client_keys WHERE id = ?`,成功后刷新快照。理由：表里没有需要保留的历史字段。软删除会让「已删密钥」仍占名字。

备选是加 `deleted_at` 列。它需要改查询与唯一性判断，收益只是留痕。要留痕应该另建审计，不塞进密钥表。

### 2. 名称确认在前端阻断

确认弹窗要求输入完整名称。不匹配时确认按钮 `disabled`。后端仍只按 id 删除，不重复校验名称。

理由：这一步的用途是防误触，不是权限控制。把名称再传到后端只会多一个可绕过的校验点。

### 3. 列表只留对外字段

模型目录去掉 Provider 与上游模型名，密钥去掉前缀。两列在编辑弹窗里仍可见可改，信息没有丢失。

备选是保留但默认隐藏。它需要列设置 UI,与当前规模不匹配。

## Risks / Trade-offs

- **删除后旧会话仍引用该密钥 id** → 会话标识里的前缀是历史事实，删除不回收。列表只按现有密钥映射名称，删除后的会回落为串号显示。
- **名称确认对长名称不便** → 名称通常很短。若以后变长，可改为二次点击确认。
- **误删不可恢复** → 确认框已要求输入名称，且弹窗写明不可撤销。

## Migration Plan

无迁移。回滚为撤销路由与查询、恢复表格列。

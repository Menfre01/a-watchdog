# Design

## Context

见 `proposal.md` 的 Why。请求原文已按 `request_bodies` 存 gzip，响应沿用同一套压缩与异步写入。

## Decisions

### 1. 旁路复制，不改转发

观察器已在逐块读取响应做用量解析。这里顺带追加到内存缓冲，达到上限即停。转发路径不变，客户端不受影响。

### 2. 异步写入

响应随请求记录进同一队列，由写协程落库。队列满时丢弃并计数，绝不阻塞请求。

### 3. 只存原始字节

解析放在读取侧。协议演进时不用迁移数据，解析失败也不影响原始内容。

### 4. 截断与完整性分开标记

超限只截断，标记 `truncated`。客户端中断时标记 `complete=0`。两者含义不同，不合并。

## Risks / Trade-offs

- **内存占用**：待写队列元素可达 2 MB。队列深度已有上限。
- **旧数据无响应**：界面标「未记录」，不回填。

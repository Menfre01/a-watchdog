# Design

## Context

See `proposal.md` - Why。

现状：`trace.AnalyzeSession` 按时间序扫描快照，把第一步所在的链写入 `chains[0]`，随后直接令 `chains[0].Kind = ChainMain`。

管理面依赖同一假设：`pkg/admin/traces.go` 用 `chains[1:]` 给旁路链编号。前端用 `side` 与 `side_chain` 字段区分主路与旁路。

输入已按时间戳稳定排序（`pkg/admin/traces.go` 中的 `sort.SliceStable`）。链的切片顺序就是各链首次出现的先后。

## Goals / Non-Goals

**Goals:**

- 主链不再由「首步」单独决定。
- 一次性自动请求（生成标题）不再夺取主链。
- 链编号、缓存键与接口字段保持不变。

**Non-Goals:**

- 不改链归属判据（两级指纹）。
- 不改轮次边界与统计口径。
- 不回算历史数据。

## Decisions

### 决策 1：主链在链归属之后单独选出

算法：

1. 扫描全部链，按顺序找第一条满足「至少两个非重复步」的链。
2. 找到即为 `mainIdx`。
3. 全部链都不足两个非重复步时，`mainIdx = 0`。
4. 按 `mainIdx` 赋 `Kind`，其余为 `ChainSide`。

「非重复步」指 `DeltaKind != retry` 的步。重试只重复已有内容，不构成持续性；否则一次标题请求被重试就会让标题链达到门槛。

选「至少两个非重复步」而不是比较步数大小，是为了保留旧反例的正确性。27 步的监控链仍不能取代 15 步的对话链，只要对话链早出现。

备选方案「步数最多者」被否决：规范记录的实测反例会误判。

### 决策 2：旁路编号按过滤后的顺序给出

`chains` 中可能有一条一次性链排在主链之前。管理面不能再用 `chains[1:]`。

改为：遍历全部链，跳过 `Kind == ChainMain`，按遇到顺序编号 1、2、3。

这样编号仍连续，且不依赖主链位于下标 0。

### 决策 3：上下文清零的排除改用 Kind 判断

`AnalyzeSession` 目前用 `j > 0` 排除旁路链的清零标记。改为 `chain.Kind != ChainMain`。理由相同，实现不再依赖下标。

### 决策 4：时间戳并列时按稳定排序的先后

两条链首步时间戳完全相同时，沿用 `sort.SliceStable` 的结果决定先后。不引入额外的并列规则，也不比较 `seq`。

## Risks / Trade-offs

- **标题链重复出现** → 用户在会话中重命名会再发一次标题生成请求。标题链因此达到 2 个非重复步，且它是首步链，仍会被选为主链。缓解：记录该形态。若实测出现，后续提案把「门槛」改为更精确的持续性判据。
- **单轮对话加重复旁路** → 主对话只有 1 步，而监控链有 2 个非重复步时，主链会落到监控链。影响面限于单轮会话，主路本就只有 1 步。若实测出现，后续提案需要引入更强的语义判据。
- **旁路链先出现且重复** → 监控或子 agent 链的首步早于主对话，且先达到门槛时，会被选为主链。真实会话中主对话通常先出现；记录该形态，暂不引入额外规则。
- **单轮会话** → 三条链都不足两个非重复步时退回首步判据，仍可能选到标题链。影响面限于单轮会话，主路本就只有 1 步，读者可见的统计差异小。
- **旁路编号变化** → 修复后原本的「旁路 #1」可能变成「旁路 #2」。编号本身是推断属性，规范未承诺稳定。

## Migration Plan

无数据迁移。链归属在查询时计算，结果按会话缓存。进程重启后自然生效。

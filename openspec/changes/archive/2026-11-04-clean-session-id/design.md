# Design

## Context

见 `proposal.md` 的 Why。存储键是 `<key_id>:<标识串>`([pkg/trace/session.go](../../../pkg/trace/session.go) 的 `ResolveSession`)。标识串字符集限定为 `[A-Za-z0-9._-]`,不含冒号，所以首个 `:` 必是分隔符。列表接口已接受 `key_id` 参数，但它会覆盖 `q`。

## Goals / Non-Goals

**Goals:**

- 界面显示的标识与客户端手里的一致。
- 密钥维度可用筛选表达，且能与前缀叠加。

**Non-Goals:**

- 不改存储格式，不做数据迁移。
- 不改轨迹详情接口的路径参数。

## Decisions

### 1. 存储不动，显示层拆分

前缀承担跨密钥的唯一性，删掉它会让两把密钥的同名会话相撞。拆分放在前端显示层：按首个 `:` 切成密钥 id 与原始标识。代价是前端要知道这个约定，因此拆分只写一处工具函数。

备选是把 `key_id` 拆成独立列。它更干净，但要迁移、回填、改查询与多处消费方，与本轮目标(显示清晰)不成比例。

### 2. 两个过滤条件各用各的参数

`key_id` 只筛密钥，`prefix` 只匹配冒号之后的原始标识。SQL 用 `substr(session_id, instr(session_id, ':') + 1)` 取标识段。理由：界面显示什么，搜索就匹配什么。若把密钥拼进前缀，未选密钥时搜 `491b` 会落空，显示与搜索对不上。

备选是前端拼接前缀再发一个 `q`。它让前端依赖存储格式，两个条件还会互相覆盖，已否决。

### 3. 详情仍用完整标识请求

详情、摘要与 step 接口的路径参数保持完整值。显示层只处理显示，不碰请求。

## Risks / Trade-offs

- **前端与存储格式耦合** → 拆分集中在 `web/src/session.ts` 一个函数，后端改格式时只改这一处。
- **标识本身含冒号**(规范外输入) → 首个 `:` 仍是密钥分隔符，剩余部分整体当标识，显示不受影响。

## Migration Plan

无迁移。回滚为撤销显示层拆分与筛选控件。后端叠加逻辑独立可回退。

# Design

## Context

见 `proposal.md` 的 Why。骨架接口已返回每步 `latency_ms` 与轮次时长。工具事件按 `tool_call_id` 配对。提示事件带提交时刻。

## Goals / Non-Goals

**Goals:**

- 三段口径写清，读者不必自己相加。
- 时间轴上的工具段位置与模型条严格相接。

**Non-Goals:**

- 不把工具段细分到单个工具。
- 不把审批等待从工具段里扣出来。

## Decisions

### 1. 后端按步归并工具时长

`attachToolDurations` 把工具事件配对成时长，再按 `trace.ToolCall.IssuedSeq` 归并到骨架的步上，字段名 `tool_ms`。理由：前端没有工具调用与步的对应关系，只有后端分析里有。

### 2. 人段在前端计算

提示事件与步时间都在前端可得。每条提示减去此前最后一次响应结束即得人的间隔。首次提示没有前序响应，不计。

### 3. 两段合计改为行内数字

色条要求读者先看形状再下钻，而结论必须去工具聚合里找。改成两个数字加一个工具占比，信息密度更高，也不受钩子覆盖率影响。

## Risks / Trade-offs

- **时间轴总长不覆盖工具段** → 工具段可能被裁到轴末端。文字仍给完整数值。
- **人的间隔含客户端处理** → 提交时刻比按键稍晚，误差可接受。
- **多工具同上一步** → 归并成一段，不逐个展示。

## Migration Plan

无迁移。回滚为删除构成条与工具段。

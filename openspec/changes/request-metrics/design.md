# Design

## Context

见 `proposal.md` 的 Why。`requests` 表已有时间、状态码、错误类型、延迟与 token 字段，聚合不需要迁移。

## Goals / Non-Goals

**Goals:**

- 一眼回答「窗口内请求是否健康」。
- 分位数与平均都给出，长尾不被抹平。

**Non-Goals:**

- 不做按模型 / 密钥的拆分，本轮只给整体。
- 不做 TTFT：流式首字延迟尚未采集。

## Decisions

### 1. 汇总交给 SQL，分位交给 Go

计数、错误数、token 求和用一条聚合查询。延迟分位需要全部样本，用一条升序查询后在 Go 里取第 `ceil(0.95×n)` 个。样本量在本机规模下可接受。

备选是 SQL 窗口函数求分位。它少一次传输，但可读性差，且 SQLite 版本差异带来风险。

### 2. 缓存命中率用「缓存 ÷（输入 + 缓存）」

分母含缓存读取，与上游计费口径一致。分母为 0 时返回 0。

### 3. 时间构成降级为行内数字

色条要求读者先看形状再下钻，而结论必须去工具聚合里找。改成两个数字加一个占比，信息密度更高。

## Risks / Trade-offs

- **样本少时分位失真** → 界面说明少于 20 个样本时参考意义有限。
- **窗口边界按请求开始时间** → 跨窗口边界的慢请求会归入开始时刻所在窗口。
- **不含 TTFT** → 流式首字慢的问题暂时看不出来。

## Migration Plan

无迁移。回滚为删除接口与岛。

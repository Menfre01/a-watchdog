# trajectory-analysis Specification

## Purpose
定义从快照序列推断会话结构的行为:链归属、相邻 step 的增量分类、轮次分组与 tool 调用抽取——全部在查询时计算,不向数据层写入任何派生结果,规则迭代不要求改动数据。

## Requirements

### Requirement: 增量分类

系统 **必须(MUST)** 对同一链内相邻快照做行级比对(输入为快照的行指纹序列与行长度序列),并把该 step 分类为:追加(本次序列是上次的前缀延伸)、重复(与上次序列完全相同)、分叉(前缀相同但尾部被替换或删除)、改写(无有效共同前缀但存在共享尾部)、无重合(既无共同前缀也无共享尾部)。

**必须** 进一步识别三种形态:**摘要压缩**(序列显著变短且旧序列末尾被保留)、**上下文清零**(序列几乎清空;**仅主链**,旁路请求没有"上下文"可言)与**末行更新**(行数不变且只有末行不同)。末行更新 **不得** 限定方向:变长、变短与等长改写都算,方向 **必须** 由末行在两侧的字节数给出。行长度序列不可用时 **必须** 只陈述「末行被更新」,**不得** 断定为「字节数不变」。

分叉形态 **必须** 给出首个分歧行在两侧的字节数与实际内容,供查看者判断该处发生了什么——**不得** 仅凭长度变化推断「压缩」或「改写」等语义。

比对 **必须** 同时给出确定的行号区间——保留(公共前缀与共享尾部)、移除(旧序列其余行)、新增(新序列其余行)——区间计数供界面展示。每个分类 **必须** 附带判定理由(依据的特征:共同前缀行数、保留尾部行数、长度变化);与相近形态无法区分时 **必须** 如实说明不确定,不得给出过度确定的结论。分类、区间与理由 **不得** 作为事实持久化——**必须** 在查询时重算。

系统 **必须(MUST)** 为分叉与改写形态求出**差异块**(LCS):每块给出类型(改动 / 删除 / 新增)、两侧的行号范围与行数。**不得** 用逐位置对齐替代——消息被插入或删除后其后所有行的位置都会偏移,逐位置对齐会报出一大片无关的差异。差异块 **必须** 基于**同链上一步**计算:会话内相邻的两步可能分属不同链(主路步的前一步常是旁路请求),拿它当比较对象得不出有意义的差异。

#### Scenario: 正常迭代识别为追加

- **WHEN** 一轮请求只在历史末尾追加消息
- **THEN** 该 step 被分类为追加,不产生改写或分叉标记

#### Scenario: 尾部替换识别为分叉

- **WHEN** 一轮请求在共同前缀之后替换或删除了尾部消息
- **THEN** 该 step 被分类为分叉,并给出首个分歧位置

#### Scenario: 历史改写识别为改写

- **WHEN** 一轮请求的历史被整体替换(前缀与尾部均不匹配)
- **THEN** 该 step 被分类为改写,并给出前后行数变化

#### Scenario: 规则迭代不需改动数据

- **WHEN** 分类规则调整后重新查询
- **THEN** 结果按新规则呈现,数据层无任何改动

#### Scenario: 重发同一请求识别为重复

- **WHEN** 一轮请求的消息内容与上一轮完全相同
- **THEN** 该 step 被分类为重复,并计入同一组的重复次数

#### Scenario: 摘要压缩可被识别并描述

- **WHEN** 一轮请求的历史被替换、序列显著变短且旧序列末尾被保留
- **THEN** 该 step 被标记为摘要压缩,并给出行数变化与保留/移除/新增的行数

#### Scenario: 上下文清零可被识别(仅主链)

- **WHEN** 主对话在新一轮请求中几乎清空历史(如 `/clear`)
- **THEN** 该 step 被标记为上下文清零,不与普通改写混同;旁路链不产生该标记

#### Scenario: 末行更新双向可辨

- **WHEN** 本步与同链上一步行数相同,且只有末行内容不同
- **THEN** 该 step 被标记为末行更新,并给出末行在两侧的字节数;末行变长与变短都算该形态,不因方向不同而退回笼统的分叉

#### Scenario: 行长度不可用时不给方向

- **WHEN** 快照只落行指纹、行长度序列不可用,而本步属于末行更新
- **THEN** 判定理由只说明末行被更新,不给方向,也不声称字节数不变

#### Scenario: 分叉给出对照内容

- **WHEN** 某 step 被分类为分叉
- **THEN** 给出差异块:每块的类型、两侧行号范围与行数;不标注「压缩」等未经证实的语义

#### Scenario: 消息被删除或新增各自成块

- **WHEN** 本步相对同链上一步删除了若干消息,或在其间插入了若干消息
- **THEN** 删除与新增各自成为独立的差异块,块内标明只有单侧的行号范围与行数

#### Scenario: 差异基于同链上一步

- **WHEN** 某步在会话内的前一步属于另一条链(如旁路请求)
- **THEN** 其差异块仍与该步**同链的上一步**比较,不拿跨链的前一步充当比较对象

#### Scenario: 分类附带判定理由

- **WHEN** 查看者查看某个 step 的分类
- **THEN** 可见该分类的依据(共同前缀、保留尾部、长度变化),无法进一步区分时如实说明不确定

### Requirement: 链归属

系统 **必须(MUST)** 在轮次分组之前完成链归属:一个 session 内可能交错着多条消息链(每轮的安全监控、并行子 agent 等),它们带同一会话标识但与主对话不相交。

判据是两级的**首条消息指纹**:

1. **system 指纹**定「请求类型」——`system` 消息剔除易变注解(`cache_control`、配额计数行)与客户端版本号后取前若干字符;同类型的各次调用指纹相同,不同类型(主对话 / 安全监控 / 子 agent / 生成标题)互不相同。
2. **首条 user 文本前缀的指纹**定「同类型内的实例」——3 个并行子 agent 共用同一套 system prompt,靠各自的任务描述区分。

两级都相同才归入同一条链;任一级缺指纹时跳过该级。**必须** 只用消息本身判定,**不得** 解析客户端特有的标记(如 `<system-reminder>` 之类),也不得跟踪工具调用关系——判据须与协议无关。**必须** 按时间戳排序后再归属:`seq` 是写入序,并发请求下与发起序不一致。

链归属完成后 **必须** 选定主链。主链 **必须** 是至少有两个非重复步的链中时间最早的一条。没有这样的链时,主链 **必须** 是含会话首步的链。其余链为旁路链。

「至少两个非重复步」只作门槛,判断依据是该链在会话内的非重复 step 条数达到 2。重复步(重试)不计入。**不得** 比较各链的步数大小。步数与上下文长度 **不得** 参与主链选择。

#### Scenario: 旁路请求与主对话分列

- **WHEN** 客户端每轮发出一次安全监控请求(独立 system prompt + 当前对话转录)
- **THEN** 该请求归入独立的旁路链,不与主对话混为一条链

#### Scenario: 并行实例各自成链

- **WHEN** 会话同时运行 3 个子 agent,它们共用同一套 system prompt 但任务描述不同
- **THEN** 三者各自成为一条旁路链;仅凭 system 指纹会把它们合成一条,故二级判据必需

#### Scenario: 一次性首步不夺取主链

- **WHEN** 会话的第一步是一次性自动请求(如生成标题),主对话与安全监控在其后反复出现
- **THEN** 一次性请求所在的链为旁路链
- **THEN** 最早出现且反复出现的链为主链
- **THEN** 步数与长度都不参与选择(实测:标题链 1 步先到;27 步的监控链超过 15 步的对话链;45 行的子 agent 链超过 42 行的主对话链)

#### Scenario: 重试不构成持续性

- **WHEN** 一次性自动请求失败后由客户端重试一次
- **THEN** 该链的非重复步仍为 1,不参与主链竞争
- **THEN** 主链是至少有两个非重复步的对话链

#### Scenario: 主链为含会话首步者

- **WHEN** 会话内没有至少两个非重复步的链,例如单轮对话伴随一次监控与一次生成标题
- **THEN** 含会话首步的链为主链

#### Scenario: 并发下按时间戳归属

- **WHEN** 多个请求并发完成,写入序号与发起时间不一致
- **THEN** 链归属按时间戳进行,不受写入序影响

### Requirement: 轮次推断

轮次分组 **必须(MUST)** 在链内判定:一个轮次由一个或多个 step 组成,边界 **必须** 由「分类为追加**或分叉**、且新增尾部含非 `tool_result` 的 user 消息」推断——分叉同样要看尾部,因为客户端每轮刷新注入内容会让纯追加退化为分叉。

**必须** 维护客户端注入内容的排除表——命中排除表的尾部消息 **不得** 开启新轮次,包括:harness 的提示类注入(如 `<system-reminder>`)、斜杠命令的展开内容、子 agent 完成时注入的结果(实测形态以 `Another Claude session sent a message:` 开头,它是**发起该子 agent 那一轮的延续**,同一诉求从"派出"到"汇总"应为一个轮次)。

分类为重复的 step **不得** 开启新轮次,**必须** 留在当前轮次内并按组内序号呈现重复计数(判据是内容完全相同,不必然是失败后重发)。**旁路链的 step** **必须** 与主路分列呈现(界面在轮次内以切换控件区分),**不得** 混入主路轮次、**不得** 参与轮次边界判定、**不得** 计入主路的轮次统计;重复组 **必须** 按链统计,不跨链。分组结果 **不得** 持久化,**必须** 在查询时推断,推断属性 **必须** 在界面上可辨识(统一的样式或图例),不要求逐条重复标注。

#### Scenario: 多步轮次被合并

- **WHEN** 一轮用户诉求引发连续多次工具迭代(每次迭代一个请求)
- **THEN** 这些 step 归入同一轮次,不因 step 数量而拆分

#### Scenario: 新用户输入开启新轮次

- **WHEN** 追加或分叉的尾部包含非 `tool_result` 的 user 消息,且不在排除表内
- **THEN** 该 step 开启新轮次

#### Scenario: 注入内容不开启新轮次

- **WHEN** 追加的尾部是客户端注入的提示类消息(命中排除表)
- **THEN** 该 step 仍留在当前轮次内

#### Scenario: 子 agent 结果不开启新轮次

- **WHEN** 子 agent 完成后其报告由 harness 注入主对话
- **THEN** 该 step 留在发起该子 agent 的轮次内,不另开一轮

#### Scenario: 重复并入当前轮次

- **WHEN** 当前轮次内的请求被重发(分类为重复)
- **THEN** 该 step 留在当前轮次内,并按组内序号呈现重复计数

#### Scenario: 旁路请求不打断主链

- **WHEN** 客户端的监控请求插在主链的两次对话之间(带同一会话标识)
- **THEN** 主链仍按其自身的步划分轮次,不被旁路请求切断;旁路请求在其所属轮次内以切换控件与主路分列呈现,不产生额外轮次

#### Scenario: 旁路请求跟随其后主路步

- **WHEN** 客户端在发出某一步操作的同时发出一份旁路请求(两者时间戳相近,如用户提问与一次监控同为同一秒)
- **THEN** 该旁路请求归入其后主路步所在的轮次,不得并入上一轮;其后没有主路步时并入最后一轮

#### Scenario: 推断属性可辨识

- **WHEN** 查看者打开轨迹详情
- **THEN** 界面以一致的方式标明哪些内容为推断(统一样式的徽标或图例),不必逐条重复标注

### Requirement: tool 调用抽取

系统 **必须(MUST)** 从快照抽取 tool 调用明细:以 `tool_use` 的标识关联发起调用的 step,并按标识与后续快照中的 `tool_result` 配对,得出每次调用的名称、入参、结果与状态;抽取结果 **不得** 持久化,**必须** 在查询时计算。

#### Scenario: 调用与结果配对

- **WHEN** 一轮 assistant 消息含 tool_use,后续请求含对应标识的 tool_result
- **THEN** 该调用呈现为一个明细条目,含名称、入参、结果与状态

#### Scenario: 无结果的调用如实呈现

- **WHEN** tool_use 存在但在后续快照中找不到对应标识的 tool_result
- **THEN** 该调用仍被列出并标记为「结果未见」,不伪装为成功

#### Scenario: 一轮内多次调用

- **WHEN** 一轮 assistant 消息含多个 tool_use
- **THEN** 每个调用单独成条,按出现顺序排列
